# Result Folder Cleaning Contract

This document is the deletion contract for the result folder cleaner. It is intentionally conservative: if a file is required for a workflow to resume without re-running an earlier expensive step, Basic clean must keep it. Deep clean keeps only user-facing deliverables and should require preview plus confirmation.

## Implementation Status

The executable cleaner is enabled only for audited workflow roots and refuses to preview when the selected workflow/root pair is ambiguous. A generic filename whitelist is not safe: for example, DIA Marker Basic clean must keep `marker/marker.parquet`, which is read by `DiaMarkerHeadlessRunner` after the first marker search and by the deep per-file marker workflow.

The selected path must be one exact workflow result root, such as `<output>/pfind_IGC_search`, `<output>/marker_comprehensive`, or a validated arbitrary DIA Target/Real-time root. Parent output folders are refused when nested workflow roots are detected. This is deliberate: a parent folder can contain multiple workflows with different restart boundaries, so cleaning it as one tree would require assumptions.

## Global Rules

| Rule | Basic Clean | Deep Clean |
| --- | --- | --- |
| Parameter files | Keep the workflow parameter JSON files stored in the selected result tree. These files are needed to reproduce the run configuration. | Delete unless they are in a final deliverable folder or protected DIA Target top-level asset. Deep clean is deliverable-oriented. |
| Converted spectra | Keep by default. For pFind, FragPipe, and Sage workflows these are often the first search-ready inputs. Removing them breaks the Basic clean promise that a rerun only regenerates missing downstream files. | May delete only if the user checks the converted spectra option and the files are inside the selected result tree. Never delete raw files or converted files outside the selected tree. |
| Unknown files | Keep in Basic unless they are known temporary/cache files. Basic clean must prefer saving less space over losing resumability. | Delete only after preview. Deep is allowed to be aggressive inside detected workflow roots, but must keep all deliverables in this document. |
| Symlinks | Do not follow symlinks for deletion. | Do not follow symlinks for deletion. |
| Final report folders | Keep the entire `report/` folder, including `report/reports/`. | Keep the entire `report/` folder, including `report/reports/`. |

## DDA MAG Workflows

MAG workflows create one workflow root plus one folder per raw/sample under that root. A sample folder name is derived from the raw file metadata. The sample-level folders are required for Basic clean because marker search and sample-specific database search are separate expensive steps.

**Layout note (all three DDA MAG engines, as of the `search_results/` nesting change):** pFind, FragPipe, and Sage now nest every per-sample folder one level deeper, under `<engine>_MAG_search/search_results/<sample>/`, instead of writing `<sample>/` directly as a sibling of `combined/`, `taxonomy_analysis/`, `functional_annotation/`, and `report/` - mirroring how DIA nests per-file folders under `marker/`. The wrapper is named `search_results`, not `marker`, because each sample folder already has its own `marker/` subfolder for marker-gene search output, and reusing the name would be confusing. `MagResultLayoutUtil` (metapilot-core, package `uk.ac.quadram.metapilot.core.mag`) auto-migrates pre-existing flat-layout result folders into `search_results/` the first time the run touches them - unconditionally, not gated on quantification having finished, because every engine's per-sample resume checks (marker search, sample-specific FASTA extraction, sample-DB search) run *before* quantification and need to find already-completed per-sample work regardless of whether `combined/` exists yet. This is safe because migration only ever runs once per run, synchronously, before any per-sample search step starts, so there is no concurrent writer for that run to race.

pFind, FragPipe, and Sage reach this migration point differently, reflecting how differently their engines are architected. pFind and Sage's per-sample resume logic lives inline in their GUI task classes (`DDAMagPfindTask`, `DDAMagSageTask`), both of which call `MetaPilotMagTask.createSeparateFolders()` once at task construction - the shared base class method that resolves `search_results/` and runs the migration. FragPipe's GUI task (`DDAMagFragPipeTask`) is a thin wrapper that delegates the entire workflow - including all per-sample resume logic - to `MagFragPipeHeadlessRunner` (metapilot-core), which is also the same class every CLI/HPC caller (`mag-fragpipe` command, `HpcStudyRunner`) uses; migration for FragPipe happens once inside `MagFragPipeHeadlessRunner.runInternal()`, before its parallel per-sample marker-search step starts, so it is never raced by its own parallel worker threads either. Neither pFind nor Sage has a CLI/HPC entry point independent of the GUI task as of this change. `ResultFolderCleaner`'s path-segment matching meant `search_results/<sample>/marker/...` is treated the same way `<sample>/marker/...` was for every *existing* rule - but this exposed a pre-existing Deep clean bug for DDA MAG, not a regression from this change (see "Deep clean per-sample retention" below).

**Deep clean per-sample retention (pFind, audited and fixed):** before this fix, Deep clean's generic "delete everything that isn't a documented final deliverable" rule deleted the entire `search_results/` tree for DDA MAG, because no keep-rule ever matched anything inside a sample folder - this was true for the old flat `<sample>/` layout too, it was not introduced by the `search_results/` nesting. A full read-trace of `DDAMagPfindTask` (see table row below) showed several per-sample files are read back by later steps within the same run (marker search feeds FASTA extraction; sample-DB search feeds PSM combination, isobaric quantification, and the `exportReport()` fallback file-list scan when `ExperimentalDesign.tsv` is missing). Deleting them in Deep clean would silently force a full re-search on any future rerun/resume. `ResultFolderCleaner.isPfindMagPerSampleDeepDeliverable()` now keeps those specific files even in Deep clean; `isPfindMagGenomeSelectionAudit()` explicitly keeps the genome-selection audit TSVs (`*_evidence.tsv`, `*_ranked.tsv`, `*_selected.tsv`) in Basic clean. Both are scoped to `WorkflowType.DDA_MAG_PFIND` only and match by the last one or two path segments, so they apply equally to the current `search_results/<sample>/...` layout and any not-yet-migrated legacy `<sample>/...` layout. FragPipe and Sage have not yet been audited for the same Deep-clean gap.

**Deep clean `combined/` narrowing (pFind, audited and fixed):** the pre-existing generic rule `isDdaCombinedDeliverable()` keeps every `.tsv`/`.txt` file directly under a workflow's `combined/` folder, in every mode - for pFind DDA MAG that means `psms.tsv`, `QuantifiedPeptides.tsv`, `QuantifiedProteins.tsv`, `QuantifiedPeaks.tsv`, `ms2_intensity.tsv`, `id.tsv`, and the isobaric `IsobaricQuantified*.tsv` outputs were all kept even in Deep clean, which defeats the point of Deep clean for a folder that is usually small relative to `search_results/` but still adds up. Only two of those files actually gate anything: `combineResults()` skips re-merging every sample's PSMs when `combined/psms.tsv` exists and is over 200 bytes, and `lfQuant()` skips re-running FlashLFQ when `combined/QuantifiedPeptides.tsv` exists and is non-empty - every other `combined/` file is regenerated from `psms.tsv` and isn't itself checked by any resume logic. `ResultFolderCleaner.isPfindMagDeepCombinedFile()` now narrows Deep clean's `combined/` retention to exactly those two files for `WorkflowType.DDA_MAG_PFIND`; Basic clean is unaffected and still keeps every `combined/` file via the unchanged generic rule.

**FragPipe (audited and fixed, same two gaps as pFind):** a full read-trace of `MagFragPipeHeadlessRunner.runInternal()` found the identical Deep-clean gaps, plus one difference worth flagging. Per-sample: `runStepAParallel()` skips a sample's marker search when `search_results/<sample>/marker/<expFolder>_1/psm.tsv` already has content, and that same file is a required input to Step B's genome selection on every run (not skip-gated - `selectGenomes()` recomputes `marker/*_evidence.tsv`/`*_ranked.tsv`/`*_selected.tsv` every time Step B runs for a sample, regardless of whether they already exist, unlike pFind); `search_results/<sample>/marker/<sample>.fasta` gates Step B's FASTA-rebuild sub-step and is the search database Step C needs on rerun; `runStepCParallel()` skips a sample's sample-DB search when `search_results/<sample>/sample_db/<expFolder>_1/protein.fas` already has content, and that same file is required to build `combined/combined.fasta`. Note `psm.tsv` and `protein.fas` sit one level deeper than pFind's equivalents - inside FragPipe's own per-experiment output folder (`marker/<expFolder>_1/psm.tsv`, not `marker/psm.tsv`) - `isFragpipeMagPerSampleDeepDeliverable()` matches by grandparent segment for those two and by parent segment (like pFind) for the FASTA. Combined: `combined/combined_modified_peptide.tsv` gates the entire combined FragPipe search (the expensive step), and `combined/combined.fasta` gates rebuilding the combined FASTA from every sample's `protein.fas`; both are kept by `isFragpipeMagDeepCombinedFile()`. Unlike pFind, `combined/combined_protein.tsv` is **not** kept in Deep clean - grepping the whole codebase found nothing that ever reads it back (the root-level `final_peptides.tsv`/`razor_proteins.tsv`/`all_proteins.tsv` deliverables are built from `combined_modified_peptide.tsv` alone), so it does not meet the "gates something" bar and deep clean discards it, same as `combined/raws.fp-manifest` and `combined/combined.workflow` (both unconditionally rewritten only when the combined search actually reruns, never on the skip path).

**Correction - `combined/<expName>/psm.tsv` (found via a real runtime bug report, not caught by the original audit):** the first version of the FragPipe Deep-clean fix above deleted `combined/<expName>/psm.tsv` - one such subfolder per experiment in the combined manifest, named after that experiment's intensity column title in `combined_modified_peptide.tsv`, produced by the combined FragPipe search itself alongside `combined_modified_peptide.tsv`/`combined_protein.tsv`. `FragpipePepReader.getPSMs()` (used by `FragpipePostAnalysisTsvExporter`, which Step G calls on every run, including a run where Step D/E/F's combined search was itself skipped because `combined_modified_peptide.tsv` already existed) reads PSM-level fields (Hyperscore, PeptideProphet Probability, Assigned Modifications) from these files - `combined_modified_peptide.tsv` is peptide-level only and has no PSM-level detail of its own. Deleting them produced exactly the failure a live user hit: `final_summary`/report generation logged `peptides=31710, psms=0` on a rerun, because the combined search's own resume check only looks at `combined_modified_peptide.tsv` and had no reason to rerun and regenerate the missing `psm.tsv` files. `isFragpipeMagDeepCombinedFile()` now also keeps `combined/<any-subfolder>/psm.tsv`. This gap existed only because the original audit traced `MagFragPipeHeadlessRunner.runInternal()` but not what `FragpipePostAnalysisTsvExporter`/`FragpipePepReader` do with `combined_modified_peptide.tsv` once Step G reads it.

Sage has not yet been audited for these two Deep-clean gaps.

## Converted Spectra Policy

The converted spectra option should be shown separately from Basic/Deep mode.

| Workflow family | Converted/search-ready spectra patterns | Default | Reason |
| --- | --- | --- | --- |
| pFind DDA IGC and pFind DDA MAG | `pf2/`, `ms2/`, `mgf/`, `rt.txt`, `ms2Count.txt` under `metaPar.getSpectraFile()` | Keep | `PFindSpectraConvertTask` creates these files before search. pFind result readers and quantification tasks also use the converted spectra path. |
| FragPipe DDA IGC | `<raw>.mzML`, optional `<raw>.mgf`, `rt.txt`, `ms2Count.txt` under the configured spectra folder | Keep | FragPipe searches use mzML; DBReducer may use MGF. The retention-time and MS2-count files are used by downstream reporting. |
| Sage DDA IGC and Sage DDA MAG | `<raw>.mzML`, optional `<raw>.mgf`, `rt.txt`, `ms2Count.txt` under the configured spectra folder | Keep | Sage searches use mzML, DBReducer may use MGF, and post-analysis uses `rt.txt`/`ms2Count.txt`. |
| DIA | Raw-adjacent `.dia` files generated from `.raw` or `.wiff`, plus original `.dia`, `.d`, or `.mzML` inputs | Keep | The first step can be conversion outside the result folder. The cleaner must not delete files outside the selected root. |

If the user checks "Remove converted spectra", the preview must mark those entries with a warning such as: "Removing converted spectra saves space, but Basic clean will no longer resume from the first search-ready step; rerun may reconvert spectra."
The executable cleaner treats `.mzML` and `.mzXML` as removable converted spectra only inside recognized converted-spectra folders such as `mzml/`, `spectra/`, or `converted_spectra/`. This avoids deleting original `.mzML` inputs stored directly inside a selected result tree.

## Implementation Implications

1. Basic clean must be profile-driven by workflow, not a generic filename whitelist.
2. Basic clean should use deny-by-default deletion: keep unknown files inside detected workflow roots unless they match explicit temporary patterns.
3. Deep clean can use an allowlist of deliverables, but the allowlist must include workflow-specific DIA combined matrices and DDA combined search-result tables when those are the only nested result tables in the selected workflow root.
4. The preview should show the interpreted root, detected workflow, kept resume checkpoints, kept deliverables, converted spectra status, and all deletion candidates before enabling Confirm.
5. The cleaner should write a log after deletion containing timestamp, selected root, workflow profile, mode, converted spectra option, deleted paths, kept paths, and warnings.
